### Environment facts (do not re-derive)

- Work dir: `C:\dev\libuipc`; LC source `C:\dev\LuisaCompute` (symlink `LuisaCompute/`); **LC install in use: `C:\dev\LuisaCompute\install-msvc`** (the old clang-built `install` must not be used).
- **LC is built with MSVC**: `cmake -S LuisaCompute -B build-msvc -G Ninja ... -DLUISA_COMPUTE_USE_SYSTEM_SPDLOG=ON`, then `cmake --build C:/dev/LuisaCompute/build-msvc -j 12 && cmake --install C:/dev/LuisaCompute/build-msvc --prefix C:/dev/LuisaCompute/install-msvc`. Toolchain: CMake `D:\cmake\bin\cmake`, Ninja, VS2022 Community `vcvars64.bat`, NVCC 12.9, GPU RTX 4060.
- **LC must be built with `-DLUISA_COMPUTE_USE_SYSTEM_SPDLOG=ON`** against libuipc's vcpkg spdlog/fmt (see cookbook §1.3), otherwise `fmt::v10` is defined twice and every backend TU fails to compile.
- **Two local LC fixes are applied**, both reproducible from this repo: the rebuild-from-source requirement of cookbook §1.2, and `scripts/patch_lc_double_transcendentals.py` (cookbook §1.4), which stops LC's *default* CUDA codegen from evaluating double `log/exp/pow/trig` through the float `lc_*` functions (a real ~1e-8 accuracy loss in every ported constitutive routine). Rebuild + reinstall LC after applying it. **Three deployment traps** (a stale LC runtime next to the tests, `luisa_compute_deploy_runtime`'s per-target cache, and the IR-keyed PTX cache at `<exe>/.cache`) will make a real LC fix look like a no-op — see cookbook §1.5.
- **The LC PTX shader cache lives next to the executable** (`build/Release/bin/.cache`) and is keyed by kernel IR, not by the builtin source — purge it after any `cuda_builtin/*.h` change (cookbook §1.5), and expect a full re-JIT afterwards.
- libuipc in-tree build: `CMAKE_TOOLCHAIN_FILE=C:/dev/vcpkg/scripts/buildsystems/vcpkg.cmake`, `-DUIPC_USING_LOCAL_VCPKG=ON -DUIPC_WITH_LUISA_BACKEND=ON`; vcpkg deps installed in `build/vcpkg_installed`.
- **Windows module export policy (T6.3b3, do not re-derive):** the `luisa` module no longer uses `WINDOWS_EXPORT_ALL_SYMBOLS` (the auto-generated list reached **69295** and MSVC caps the export table at 65535 → `LNK1189`; the T6.3b2 tree sat at 65482, i.e. 53 below). It links with the explicit, checked-in `src/backends/luisa/luisa_module.def` (`LINK_DEPENDS` + `/DEF:`), maintained by `python scripts/luisa_module_def.py` (`--check` = rc 1 when stale); the rebuilt DLL exports **502** symbols. A test that uses a new backend symbol now fails the **link** with an unresolved external — re-run that script and commit the refresh. The four C entry points are `UIPC_BACKEND_API` (`dllexport`) and are validated dynamically by `python scripts/luisa_check_module_abi.py` (LoadLibrary + GetProcAddress; in the battery since T6.3b3).
- **Known harness hazards (T6.3b3):** a failing `UIPC_ASSERT` in `do_build`/`do_init` **aborts** the test process (rc 3221226505 / 0xC0000409) instead of reporting a Catch2 failure; a test-local kernel holding two or more big 12x12 `make_spd` chains **deadlocks** `luisa::compute::Device::compile`; and initialising a *second* `Engine` makes the next `frame_stream().synchronize()` SIGSEGV or hang (pre-existing; T6.4's multi-engine tests will hit it).
- The reference backend uses **`cuda_tool`**, not `muda` (see cookbook §0).
- Windows shell notes: invoke `cmd /c` from **Python** (`subprocess`) writing to a log file (MSVC output is not UTF-8 — decode with `errors="replace"`), not from MSYS bash (argument mangling); `set VSLANG=1033` for English diagnostics; MSYS heredocs turn `\` in paths into `/` and eat `\n` escapes.
